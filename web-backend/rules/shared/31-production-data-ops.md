# 生产数据操作规则

生产数据修复、手工 SQL、批量回填和备份恢复属于高风险操作，必须可审批、可预演、可回滚、可审计。

## 适用范围

1. 生产库 / 预发库的手工 `INSERT`、`UPDATE`、`DELETE`、DDL、批量修复脚本。
2. 线上数据回填、状态订正、权限修复、账务 / 订单 / 用户敏感数据修复。
3. 备份、恢复、脱敏导出、从生产复制数据到非生产环境。
4. 由定时任务、一次性 Job、控制台工具触发的批量数据变更。

## 执行前

1. 必须有工单或变更记录：背景、影响租户 / 用户、Owner、Reviewer、执行人、计划窗口。
2. 必须给出 dry-run 结果：目标 SQL / 脚本、预计影响行数、抽样校验方式。
3. 必须准备回滚或前滚修复方案；不可回滚时须明确说明风险和补偿流程。
4. 涉及 PII、账务、权限、订单、库存等数据时，必须额外确认审计日志和通知策略。
5. DDL 须评估锁表、索引构建、复制延迟、磁盘增长；大表优先 expand / migrate / contract。

## SQL 与脚本约束

1. 禁止无 `WHERE` 的生产 `UPDATE` / `DELETE`；确需全表操作必须有二次审批和分批策略。
2. `WHERE` 条件须包含业务主键、租户、状态或时间窗口等边界，不得只用模糊条件修改数据。对使用逻辑删除的表，日常修复仅处理未删除数据，并在条件中包含未删除标志；样板用户表使用 `is_deleted = 0`。只有工单明确要求修复已删除数据时，才能调整该条件。
3. 批量脚本必须幂等，可重复执行；每批记录 traceId / jobId、影响行数、失败原因。
4. 高风险脚本先在只读查询模式输出候选记录，再切换执行模式。
5. 禁止在聊天工具中直接粘贴可执行生产密钥、连接串或完整敏感数据。
6. 对包含 `version` 的表，手工 `UPDATE` 和回滚都必须执行 `version = version + 1`，不得恢复旧版本；否则，应用已读取的旧版本仍可能覆盖本次修复。执行时将 `updated_by` 写为操作人，回滚时恢复备份值。该列可空，核对逻辑须将两侧同时为空视为一致。

## 执行中与执行后

1. 执行时记录开始 / 结束时间、执行人、变更版本、影响行数、异常信息。
2. 执行后必须抽样校验，校验 SQL 与结果写回工单。
3. 发现影响行数与预期不一致，立即停止后续批次并通知 Owner。
4. 重要修复须补充自动化测试、迁移脚本或产品流程，避免反复手工修复。

## 备份与恢复

1. 备份须加密、设定保留周期和访问控制，遵守 `29-data-privacy-lifecycle.md`。
2. 关键系统须定期做恢复演练；不能只证明“有备份”，必须证明“能恢复”。
3. 从生产恢复到非生产环境前必须脱敏，禁止把真实 PII 进入测试 fixture。
4. **RTO / RPO**、演练频率、恢复审批与校验清单见 `docs/backup-restore-runbook.md`；可靠性目标见 `32-service-reliability.md`。

## AI 生成约束

1. AI 可以生成数据修复 SQL / 脚本草案，但必须附带 dry-run、影响行数校验、回滚方案和人工审批提醒。
2. AI 不得把草案描述为“可直接生产执行”。
3. AI 发现用户要求绕过审批、备份、回滚或审计时，必须拒绝并给出安全流程。

执行清单见 `docs/backup-restore-runbook.md`。以下 SQL 是可复制的单租户（`NONE`）草案，使用 MySQL 与 PostgreSQL 的公共语法。执行器先将 `:executed_at_utc` 转换为毫秒精度的 UTC 时刻，再绑定到写入和核对语句。样板用户表使用逻辑删除，且 SQL 不经过 MyBatis-Plus，因此每条读写都显式包含 `is_deleted = 0`。状态更新和回滚均执行 `version = version + 1`，并将 `updated_by` 写为操作人。执行前必须有工单、Owner 复核、dry-run，以及回滚或前滚方案。

```sql
-- Ticket:
-- Owner:
-- Reviewer:
-- Environment:
-- Planned window:
-- Expected affected rows:
-- Rollback / forward-fix:
-- Batch size (:batch_size):
-- UTC execution instant (:executed_at_utc, generated by the approved runner):
-- Truncate that Instant to millisecond precision (3 fractional digits, UTC) before binding.
-- Write and compare the same bound value. A microsecond Instant does not equal DATETIME(3).
-- The statements below use the common MySQL / PostgreSQL subset. Do not replace them with one-dialect syntax.
-- SHARED_COLUMN projects must add the trusted tenant predicate to every step.
-- sys_user is logically deleted. This SQL does not go through MyBatis-Plus.
-- Every live-row read and write includes is_deleted = 0.
-- A ticket that repairs deleted rows must say so and must not copy this predicate.
-- sys_user.version is an optimistic lock. Increment it on the fix and again on rollback.
-- Do not write the previous version back. An in-flight updateById would otherwise overwrite this change.

-- 1. Dry-run: inspect candidate rows.
SELECT id, status, updated_at
FROM sys_user
WHERE status = :old_status
  AND updated_at < :before_time
  AND is_deleted = 0
ORDER BY id
LIMIT :batch_size;

-- 2. Count: confirm affected rows before write.
SELECT COUNT(*) AS affected_rows
FROM sys_user
WHERE status = :old_status
  AND updated_at < :before_time
  AND is_deleted = 0;

-- 3. Create an empty rollback / audit table once.
-- The ticket-specific table must be new; creation must fail instead of reusing stale backup data.
CREATE TABLE ops_data_fix_YYYYMMDD_ticket_id AS
SELECT id, status, updated_at, updated_by
FROM sys_user
WHERE 1 = 0;

-- CREATE TABLE AS SELECT does not copy the primary key. The unique index blocks duplicate backup rows.
CREATE UNIQUE INDEX ops_data_fix_YYYYMMDD_ticket_id_pk ON ops_data_fix_YYYYMMDD_ticket_id (id);

-- 3b. Create the batch-key table once, before any transaction.
-- MySQL cannot open one temporary table twice in the same statement, and DROP TABLE commits implicitly.
-- Each batch only deletes and reloads rows inside the transaction.
DROP TABLE IF EXISTS ops_data_fix_YYYYMMDD_ticket_id_batch;
CREATE TEMPORARY TABLE ops_data_fix_YYYYMMDD_ticket_id_batch (
    id BIGINT PRIMARY KEY
);

-- 3c. One-row gate table. The decision query reads only this table.
CREATE TABLE ops_data_fix_YYYYMMDD_ticket_id_gate (
    expected_batch_rows BIGINT NOT NULL,
    backed_up_batch_rows BIGINT NOT NULL,
    updated_batch_rows BIGINT NOT NULL
);

-- 4. Load one bounded batch. Run steps 4-7 in this transaction.
-- Do not issue BEGIN while a transaction is open: on MySQL that commits the current transaction.
-- Repeat steps 4-7 only after the previous batch transaction has ended.
BEGIN;
DELETE FROM ops_data_fix_YYYYMMDD_ticket_id_batch;
INSERT INTO ops_data_fix_YYYYMMDD_ticket_id_batch (id)
SELECT id
FROM sys_user
WHERE status = :old_status
  AND updated_at < :before_time
  AND is_deleted = 0
ORDER BY id
LIMIT :batch_size;

-- 5. Back up only this batch before changing it. NOT EXISTS makes a retried batch idempotent.
INSERT INTO ops_data_fix_YYYYMMDD_ticket_id (id, status, updated_at, updated_by)
SELECT u.id, u.status, u.updated_at, u.updated_by
FROM sys_user u
JOIN ops_data_fix_YYYYMMDD_ticket_id_batch batch ON batch.id = u.id
WHERE NOT EXISTS (
    SELECT 1
    FROM ops_data_fix_YYYYMMDD_ticket_id backup
    WHERE backup.id = u.id
)
  AND u.is_deleted = 0;

-- 6. Update only the materialized primary keys.
-- :executed_at_utc is already truncated to millisecond precision.
-- :operator_id is the approved executor, the same type as updated_by.
UPDATE sys_user
SET status = :new_status,
    updated_at = :executed_at_utc,
    updated_by = :operator_id,
    version = version + 1
WHERE id IN (SELECT id FROM ops_data_fix_YYYYMMDD_ticket_id_batch)
  AND status = :old_status
  AND updated_at < :before_time
  AND is_deleted = 0;

-- 7. Record counts, then decide. Each statement below opens the temporary table at most once.
DELETE FROM ops_data_fix_YYYYMMDD_ticket_id_gate;
INSERT INTO ops_data_fix_YYYYMMDD_ticket_id_gate (
    expected_batch_rows, backed_up_batch_rows, updated_batch_rows
)
SELECT COUNT(*), 0, 0
FROM ops_data_fix_YYYYMMDD_ticket_id_batch;

UPDATE ops_data_fix_YYYYMMDD_ticket_id_gate
SET backed_up_batch_rows = (
    SELECT COUNT(*)
    FROM ops_data_fix_YYYYMMDD_ticket_id backup
    JOIN ops_data_fix_YYYYMMDD_ticket_id_batch batch ON batch.id = backup.id
);

UPDATE ops_data_fix_YYYYMMDD_ticket_id_gate
SET updated_batch_rows = (
    SELECT COUNT(*)
    FROM sys_user u
    JOIN ops_data_fix_YYYYMMDD_ticket_id_batch batch ON batch.id = u.id
    WHERE u.status = :new_status
      AND u.updated_at = :executed_at_utc
      AND u.updated_by = :operator_id
      AND u.is_deleted = 0
);

SELECT
    expected_batch_rows,
    backed_up_batch_rows,
    updated_batch_rows,
    CASE
        WHEN expected_batch_rows = 0 THEN 'BATCH_EMPTY'
        WHEN expected_batch_rows = backed_up_batch_rows
         AND expected_batch_rows = updated_batch_rows
        THEN 'READY_TO_COMMIT'
        ELSE 'ROLLBACK_REQUIRED'
    END AS batch_decision
FROM ops_data_fix_YYYYMMDD_ticket_id_gate;

-- BATCH_EMPTY means this batch loaded no rows. The runner issues ROLLBACK and stops.
-- COMMIT only for READY_TO_COMMIT. ROLLBACK for ROLLBACK_REQUIRED.
-- This template intentionally contains no unconditional COMMIT statement.
-- Repeat steps 4-7 only after the previous batch transaction has ended; do not remove the LIMIT.

-- 8. Verify post-condition after all batches.
SELECT COUNT(*) AS remaining_rows
FROM sys_user
WHERE status = :old_status
  AND updated_at < :before_time
  AND is_deleted = 0;

-- 9. Rollback draft. Validate with owner before use.
-- Rollback reuses the batch-key table and the gate table. Do not DROP either table.
-- These statements stay commented so executing the fix does not undo it.
-- Repeat steps 9a-9d only after the previous rollback transaction has ended.
--
-- 9a. Load one bounded rollback batch. Do not issue BEGIN while a transaction is open.
-- BEGIN;
-- DELETE FROM ops_data_fix_YYYYMMDD_ticket_id_batch;
-- INSERT INTO ops_data_fix_YYYYMMDD_ticket_id_batch (id)
-- SELECT b.id
-- FROM ops_data_fix_YYYYMMDD_ticket_id b
-- JOIN sys_user u ON u.id = b.id
-- WHERE u.status = :new_status
--   AND u.is_deleted = 0
-- ORDER BY b.id
-- LIMIT :batch_size;
--
-- 9b. Restore only the materialized primary keys from the backup table.
-- UPDATE sys_user
-- SET status = (
--         SELECT b.status
--         FROM ops_data_fix_YYYYMMDD_ticket_id b
--         WHERE b.id = sys_user.id
--     ),
--     updated_at = (
--         SELECT b.updated_at
--         FROM ops_data_fix_YYYYMMDD_ticket_id b
--         WHERE b.id = sys_user.id
--     ),
--     updated_by = (
--         SELECT b.updated_by
--         FROM ops_data_fix_YYYYMMDD_ticket_id b
--         WHERE b.id = sys_user.id
--     ),
--     version = version + 1
-- WHERE id IN (SELECT id FROM ops_data_fix_YYYYMMDD_ticket_id_batch)
--   AND status = :new_status
--   AND is_deleted = 0;
--
-- 9c. Each statement opens the temporary table at most once.
-- DELETE FROM ops_data_fix_YYYYMMDD_ticket_id_gate;
-- INSERT INTO ops_data_fix_YYYYMMDD_ticket_id_gate (
--     expected_batch_rows, backed_up_batch_rows, updated_batch_rows
-- )
-- SELECT COUNT(*), 0, 0
-- FROM ops_data_fix_YYYYMMDD_ticket_id_batch;
--
-- UPDATE ops_data_fix_YYYYMMDD_ticket_id_gate
-- SET backed_up_batch_rows = (
--     SELECT COUNT(*)
--     FROM ops_data_fix_YYYYMMDD_ticket_id backup
--     JOIN ops_data_fix_YYYYMMDD_ticket_id_batch batch ON batch.id = backup.id
-- );
--
-- UPDATE ops_data_fix_YYYYMMDD_ticket_id_gate
-- SET updated_batch_rows = (
--     SELECT COUNT(*)
--     FROM sys_user u
--     JOIN ops_data_fix_YYYYMMDD_ticket_id_batch batch ON batch.id = u.id
--     JOIN ops_data_fix_YYYYMMDD_ticket_id backup ON backup.id = u.id
--     WHERE u.status = backup.status
--       AND u.updated_at = backup.updated_at
--       AND (
--           u.updated_by = backup.updated_by
--           OR (u.updated_by IS NULL AND backup.updated_by IS NULL)
--       )
--       AND u.is_deleted = 0
-- );
--
-- 9d. Decide from the gate table only.
-- SELECT
--     expected_batch_rows,
--     backed_up_batch_rows,
--     updated_batch_rows,
--     CASE
--         WHEN expected_batch_rows = 0 THEN 'BATCH_EMPTY'
--         WHEN expected_batch_rows = backed_up_batch_rows
--          AND expected_batch_rows = updated_batch_rows
--         THEN 'READY_TO_COMMIT'
--         ELSE 'ROLLBACK_REQUIRED'
--     END AS batch_decision
-- FROM ops_data_fix_YYYYMMDD_ticket_id_gate;
--
-- BATCH_EMPTY means this rollback batch loaded no rows. The runner issues ROLLBACK and stops.
-- COMMIT only for READY_TO_COMMIT. ROLLBACK for ROLLBACK_REQUIRED.
```
