# 需求到验收证据追踪

> 目标：让每个业务变更都能回答“为什么改、改了什么、如何证明正确”。CI 只能证明确定性门禁通过，不能替代需求与业务流程判断。

## 适用范围

- 新功能、业务规则、状态流转、权限、计费、数据口径和用户可见行为变更。
- 缺陷修复且修复结果依赖特定业务前提或边界条件。
- API、数据库、配置或异步任务变更可能影响既有业务流程。

纯格式、注释或无行为变化的机械调整可以在 PR 中说明“不适用”及理由。

## 最小追踪链

每个可观察变更至少保留以下链路：

```text
需求 / Issue ID
  -> 可验收条件
  -> 设计或契约变更
  -> 实现文件
  -> 测试 / 联调 / 人工验证证据
  -> 发布与回滚证据
```

禁止只写“按需求实现”“测试通过”而没有可定位的需求、场景和证据。

## PR 追踪矩阵

将下表放入 PR 描述、需求文档或项目约定的等价系统；一条需求包含多个独立场景时应拆行。

| 需求 / Issue | 验收条件 | 影响面 | 实现 / 契约 | 验证证据 | 状态 |
|---|---|---|---|---|---|
| REQ-123 | 已授权用户可取消“待处理”订单；其他状态拒绝 | API、状态机、审计、页面 | OpenAPI diff；`OrderService`；取消按钮 | 单测名、CI URL、联调记录 | Pass |

字段要求：

1. `需求 / Issue`：可追溯 ID 或链接；临时线上修复使用事故 / 工单 ID。
2. `验收条件`：用输入、前置状态、动作和可观察结果描述，避免“功能正常”。
3. `影响面`：至少检查工作流、数据、权限、契约、兼容和发布。
4. `实现 / 契约`：指向关键文件、OpenAPI、migration、配置或 ADR。
5. `验证证据`：测试名称、CI run、截图、查询结果或联调记录；不得填写无证据的“已验证”。
6. `状态`：`Pass`、`Fail`、`Blocked` 或经批准的 `Exception`。

## 验收条件写法

每个关键场景至少覆盖：

- 正常路径：合法状态、合法角色、合法数据。
- 失败路径：校验失败、外部依赖失败、超时、重试和部分成功。
- 边界路径：空值、上限、精度、时区、分页末页和并发。
- 权限路径：未登录、无角色、非 Owner、跨租户、跨数据范围。
- 兼容路径：旧客户端、旧数据、灰度期间新旧版本并存。
- 恢复路径：取消、回滚、补偿、重放或人工处置。

## 变更控制

1. 验收条件变化必须先更新需求 / Issue 或 PR 追踪矩阵，再改实现与测试。
2. 删除或弱化验收条件须由产品 / 业务 Owner 明确确认，不能由开发或 AI 自行推断。
3. 无法获得需求原文时，先记录假设、待确认项和风险；不得声称业务正确性已确认。
4. 合并前由 Reviewer 检查矩阵是否覆盖实际 diff；发布前将关键需求 ID 写入发布证据。
