# 业务正确性评审

> Lint、测试、构建、依赖扫描和安全扫描是质量门禁，但它们不能单独证明业务功能正确。

## 评审输入

开始业务评审前至少取得：

- 需求、Issue、PR 描述或领域文档；
- 相关 OpenAPI、数据模型、状态机和权限模型；
- 变更 diff 与测试证据；
- 发布、兼容和回滚约束。

输入缺失时必须把缺口写进结论，不得用代码行为反推并宣称它就是需求。

## 七类检查

| 维度 | 必查问题 | 常见漏项 |
|---|---|---|
| 需求一致性 | 实现是否逐条满足验收条件；是否夹带未授权行为 | 只验证 happy path；范围悄悄扩大 |
| 工作流 | 状态迁移、审批、取消、重试、幂等、补偿是否闭环 | 任意 `setStatus`；部分成功无处置 |
| 数据 | 字段映射、过滤、排序、分页、精度、时区和兼容是否正确 | 跨租户、末页、金额浮点、旧数据为空 |
| 权限 | 角色、租户、Owner、数据范围和对象级授权是否同时成立 | 只隐藏按钮；详情 / 导出漏鉴权 |
| API / UI | 请求响应、校验、错误、loading 与用户可见状态是否一致 | 后端成功但前端假成功；错误码未映射 |
| 回归 | 既有流程、消费者、migration、缓存和异步集成是否受影响 | 只测新增入口；忽略旧客户端 |
| 测试 | 关键、失败、边界和权限路径是否有可复现证据 | 用“测试通过”代替测试名和结果 |

## 评审输出

评审结论按严重程度列出发现，并包含：

1. 可定位的文件 / 行、契约或配置证据；
2. 与哪条需求或验收条件冲突；
3. 对用户、数据、权限、兼容或发布的影响；
4. 可执行修复建议；
5. 缺失的测试或验证证据。

若未发现问题，应明确写“未发现确定性问题”，同时列出未覆盖的场景与残余风险。禁止把“CI 全绿”等同于“业务流程正确”。

## 合并门禁

- P0 / P1 业务问题未解决或未获有效豁免，不得合并。
- 需求追踪矩阵缺少关键场景，不得给出“业务正确”结论。
- 权限、资金、隐私、不可逆数据变更和跨租户风险须由对应 Owner Review。
- Reviewer 与实现者对需求理解不一致时，以需求 Owner 的可追溯确认作为决策证据。
