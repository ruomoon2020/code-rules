# 环境晋级与生产变更

## 核心原则

- 同一构建产物按 `dev -> test -> staging -> production` 晋级，禁止在环境之间重新构建或手工改包。
- 产物以 commit SHA 和不可变摘要标识；配置、密钥和数据迁移与代码分离管理。
- 每次晋级都要有负责人、准入结果、批准记录、观测窗口和可执行回滚路径。

## 晋级门禁

| 阶段 | 最低证据 |
|---|---|
| Dev -> Test | 单元测试、静态检查、契约检查、测试数据准备 |
| Test -> Staging | 集成/端到端测试、迁移演练、安全与依赖检查、回滚演练 |
| Staging -> Production | 验收证据、审批、产物摘要、配置漂移检查、监控与告警、发布窗口 |

生产发布使用 [`release-evidence.md`](release-evidence.md) 的结构化证据，并由 `validate-release-evidence.py` 校验。

## 配置与迁移

- 用声明式清单比较环境配置，禁止通过控制台临时修改后不回写 SSOT。
- 数据迁移须前向兼容、可重入、可观测；破坏性变更使用 expand/migrate/contract，先证明回滚或前滚策略。
- Feature Flag 必须记录 owner、目的、默认值、目标环境、启停条件和到期日；到期后删除或续期审批。

## 发布策略

- 高风险变更优先灰度、金丝雀或分批放量；每一阶段定义指标阈值和自动/人工停止条件。
- 变更冻结期仅允许经授权的紧急修复，必须记录风险、批准人、验证和事后复盘。
- 回滚命令或 runbook 必须在等价环境演练；只有“可回滚”描述而无演练证据不得进入生产。

## 完成条件

观测窗口结束、关键指标稳定、业务数据核对完成、临时权限和开关已收口、证据归档后，发布才算完成。失败或超阈值时执行停止/回滚并按 [`incident-response.md`](incident-response.md) 评估是否升级为事故。
